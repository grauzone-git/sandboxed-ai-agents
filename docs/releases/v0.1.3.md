# sandboxed-agents v0.1.3 (preview)

Preview of the standalone executable ([#36](https://github.com/grauzone-git/sandboxed-ai-agents/issues/36)). It follows the published `v0.1.2` prerelease and fixes image builds under a restrictive umask ([#51](https://github.com/grauzone-git/sandboxed-ai-agents/issues/51)), a bug found during the Linux manual validation in [#50](https://github.com/grauzone-git/sandboxed-ai-agents/issues/50). It is not a stable release. The checkout launchers remain the supported entry point until the [handover gates](https://github.com/grauzone-git/sandboxed-ai-agents/blob/v0.1.3/docs/HANDOVER.md#gates) close. Commands are unchanged from the `v0.1.0` [capabilities](https://github.com/grauzone-git/sandboxed-ai-agents/blob/v0.1.3/docs/releases/v0.1.0.md#capabilities).

## Fix

Under a restrictive umask such as `077`, `v0.1.2` wrote its embedded build context files with mode `0600`. The Containerfile copies them into the image as root-owned files, so the unprivileged `agent` user could not read the manager, and a sandbox built from that image failed during the non-root manager bootstrap. This affects every image build: `build`, `update` without `--no-build`, `adopt`, and the derived image for the `podman` capability.

The executable now sets each build context file to mode `0644` explicitly after writing it, regardless of the umask. The temporary context directory and its subdirectories stay `0700`, so the files remain private to the user on the host. The process umask is not changed. Under the common `umask 022` the result is the same as before.

A public CLI test runs `build` against a fake Podman, for a successful and a failed build, under the ambient umask and under `umask 077`. The fake Podman records the mode of every file and directory in the context, and the test requires `0644` files, `0700` directories, and removal of the context afterwards. Before the fix, both `umask 077` cases failed with all 28 context files at mode `0600`. With the fix, all four cases pass. `update`, `adopt`, and the derived `podman` image use the same build context code, confirmed by reading the source.

The full offline suite (`./tests/run`) and `go test ./...` passed locally on this change, and all three cross-builds and the Windows test cross-compile passed. Two independent source reviews of the fix found nothing actionable. At the time these notes were prepared, the documentation reviews, regular CI on the candidate commit, and the `v0.1.3` release workflow had not run, and no live Podman run had used the fix.

## Results for v0.1.2

- Regular CI run [36142463885](https://github.com/grauzone-git/sandboxed-ai-agents/actions/runs/36142463885) passed all six jobs on the tagged commit `fdae935`.
- Release run [36143411566](https://github.com/grauzone-git/sandboxed-ai-agents/actions/runs/36143411566) passed all five jobs and published the [v0.1.2 prerelease](https://github.com/grauzone-git/sandboxed-ai-agents/releases/tag/v0.1.2).
- The published `SHA256SUMS` checks pass for all three binaries, and an independent rebuild of `fdae935` matches it for all three targets.
- `gh attestation verify` passes for all three published binaries.
- The published npm archive installed, ran, and uninstalled cleanly on Linux outside the checkout, and its native binary is byte-identical to the published linux/amd64 binary.

On a real Linux host, the owner reported these steps as passing with the published linux/amd64 binary: image build, sandbox creation, SSH access, volume reuse, a bound workspace, the ownership refusals, the executable bind refusal, normal `update`, the `update` rollback, the tokentracker `tools enable` and `service status`, `forward`, the `forward` refusal without SSH setup, and the adoption setup and wrong-checkout refusal. The actual `adopt` of a checkout-owned sandbox ran under `umask 077` and failed on the bug fixed here. The CLI exited with code 1 and restored the original sandbox, and the owner's nine rollback checks passed, including the owner label, volumes, workspace marker, host key, SSH access, and SSH files. This was a real rollback after a bootstrap failure. The planned rollback attempt with controlled fault injection has not run, because the failure happened before its injection point, and no adoption has succeeded.

## Omitted commands

None. Every command listed in `sandboxed-agents --help` is implemented: `version`, `build`, `list`, `update --all`, `adopt --all`, and, per sandbox, `up`, `start`, `stop`, `restart`, `remove`, `shell`, `ssh-config`, `check`, `check-full`, `fingerprint`, `agents`, `tools`, `run`, `tool`, `service`, `forward`, `update`, `adopt`, and the session shortcuts.

## Known limitations

These are unchanged from `v0.1.0`. Linux needs rootless Podman 5+ with the host prerequisites linked above, and Windows needs Windows 11 x64 and Podman 6.0+. Only the three binaries are attested, the Windows executable is not Authenticode-signed, packages are not on npm or nuget.org, and there is no self-update command.
